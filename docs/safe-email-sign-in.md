# Prototype Safe: email/password and Google

Prototype only. The prototype Netlify Identity service is enabled with email confirmation required, public account creation enabled, and the managed Google provider enabled. Native email is not disabled. Google uses Netlify's managed provider configuration. No production Identity or Safe settings are changed.

Guests sign in with email/password or Continue with Google. Email account creation sends a confirmation link; Forgot password sends a reset link. Callbacks return to /traveler-safe, and the app-root fallback recognizes Safe OAuth flow context rather than routing it into master admin. The Identity SDK handles callback/session cookies and refresh. Callback tokens are never stored in source or logged. No emails are sent by deployment or TD assignment; provider emails occur only when the guest submits signup/recovery.

TD Suitcase → Safe email access grants access. Enter the guest's actual sign-in email. Up to four authorized emails can share one Safe, separated by commas. An email can belong to only one Safe. Saving explicitly warns that email assignment grants access to that Safe's documents/plans. Email grants are private, independent of public guest contact fields, and never inferred from a typed Safe ID, URL parameter, user metadata or first signup.

Assignments live in traveler-safe-access/assignments with a single CAS revision, stable guest/Safe IDs and per-email Identity subject bindings. The first verified login binds the assigned email to the verified Identity user ID; later logins must match it. Roster removals and email removals deny subsequent requests. TD changes require a current TD session, same origin, exact access/roster revisions and unique normalized emails. Concurrent first login can change the access revision; reload the TD form when prompted. Removing then reassigning an email resets its subject binding intentionally.

Safe authorization verifies the visitor's nf_jwt cookie directly against Identity /user, requires confirmed email, and checks the private TD assignment and current roster. It never uses an operator token or the SDK server getUser fallback. PIN activation, login and recovery POSTs return method-not-allowed. Legacy __Host-kd_safe sessions are ignored. Logout clears Identity cookies/session through the SDK and expires the legacy cookie. UI changes clear cached document lists on account changes/sign-out.

On first authorized Identity access, an existing assigned TG Safe preserves its account ID, AES key, nickname, encrypted files and plans. Legacy PIN hashes/salts/recovery fields are stripped from the migrated account. New Safes are created only for verified, TD-assigned identities. A record tied to a different guest is not reassigned automatically. Unassigned older username-only records are retained in storage rather than guessed or deleted; they need an explicit ownership migration if encountered. Private document encryption, authorization, same-origin checks, file limits and revision protections remain in place.

Validation: node tests/traveler-safe.mjs tests verified visitor vs operator handling, unverified/unassigned/foreign subjects, retired PIN access, TD grants, duplicate emails, shared ownership, revocation, cross-Safe isolation, preservation/decryption of pre-existing files and plans, CRUD, CSRF and revisions. Browser checks use the actual Identity SDK against mocked provider endpoints for signup, login, confirmation/reset redirect targets, Google callback routing, recovery/update, sign-out, no PIN UI, TD grants and phone/tablet layouts. No real guest Google account or password was used in tests. A static build is also required.

## Preferred-email invitations (prototype)

TD Suitcase → Safe invitations → Create private invitation creates a cryptographically random 256-bit, one-use link for the selected roster guest’s existing Safe. The TD shares it privately; the app never sends emails or exposes links in the guest list. Only its SHA-256 hash, roster owner and seven-day expiry are stored in the private assignments CAS record. A replacement or revocation invalidates unused links and leaves existing members intact.

A guest opens the invitation, chooses their preferred verified email or Google account, then explicitly selects Connect my Safe. The token is removed from the address bar immediately and retained only in that tab’s session storage through sign-in; after a successful claim it is deleted. If email verification opens another tab or browser, reopen the original invitation to connect. The verified Identity subject/email is added atomically to the correct Safe while consuming the token. Accounts already linked to another Safe cannot claim it. Expired, consumed, revoked, changed-roster and unverified claims fail. Existing AES keys, documents and plans are preserved by the existing migration. Up to four accounts may share a Safe; each account belongs to one Safe.

Access edits preserve pending invitations. Invitation API requires same origin, rate limits and TD authorization for issuance/revocation; claims require verified visitor identity. Realistic API tests cover expiry, one use, replacement, revocation, roster checks, cross-Safe denial and encryption-key preservation. No real guest invitations are generated during tests.
