# Live and prototype: share selected Safe items

Guests choose Share beside an existing document or a saved personal activity, enter the recipient’s sign-in email and send an in-app invitation. No email is sent. The recipient signs in and accepts under Sharing → Invitations. Accepted items appear under Shared with me; they are references to the selected source item, not copies of a Safe. People authorized to use the recipient’s Safe can access the accepted item, as the sender is told before inviting. Documents allow viewing/downloading only; activity owners may grant view-only or edit access. Owners stop access under Shared by me → Stop sharing. Recipients may remove an item. Downloaded copies cannot be recalled.

Safe names and nickname controls are removed. The account header shows only the sign-in email, and nickname PATCH requests are retired. Existing owner IDs, encryption keys, documents, plans and automatic email/Google sign-in are preserved. Both editions use the same Safe implementation.

The new /api/safe-sharing handler verifies the visitor’s Identity token and resolves their Safe with the existing server-side authorization. A private strong-consistency traveler-safe-sharing ledger holds UUID grants, source owner IDs/account keys, verified sender email, normalized recipient email, per-record version and status. Source ownership is derived from the authenticated account, never client-supplied owner metadata. Recipient acceptance binds the verified subject and destination Safe’s immutable owner ID. Accepted access follows that Safe ID, so an unrelated Identity with a recycled email cannot read an accepted item. Requests to accept within the source Safe are rejected.

Each read/download checks current grants and source existence. Source account IDs must still match the grant; document keys stay server-side. Documents are decrypted only for authorized downloads, with private/no-store responses. Pending invitations expose only selected-item metadata, never file bytes or activity notes. Other items in a source Safe are never returned. Deleted source documents/activities become unavailable rather than being recreated.

Mutations require same origin and verified session. Accept/decline/revoke use version checks and CAS writes; unrelated ledger changes retry safely. Editable plans validate the selected activity’s fields, retain its source ID/date, compare the source plan revision and replace only that one activity. The rest of the owner’s day stays untouched. Permissions are rechecked before saving. Future requests after revocation are denied; already downloaded/viewed content cannot be erased remotely. Sharing is rate limited and bounded to 100 active outgoing grants per owner and 5,000 ledger records per site.

The UI clears sharing state on owner changes/sign-out, ignores responses from old sessions, and pauses background refresh while editing a shared plan. Refresh plans reloads the owner’s current saved activities. The top-of-Safe shortcut opens invitations quickly. Share controls appear only beside saved items, not unsaved edits.

Validation: node tests/traveler-safe.mjs covers confirmed vs unconfirmed identities, pending/accepted access, normalized emails, duplicate grants, self/foreign-item attempts, AES document retrieval, cross-Safe isolation, view/edit enforcement, selected-activity-only updates, stale revisions, CSRF, revocation, leaving, deleted sources and retired name updates. Browser checks use mocked APIs and the real Identity client for invite creation, acceptance, view-only/editing UI, downloads, stopping sharing, unsaved edits surviving background events, sign-out clearing and 320/390/768px layouts. No real traveler invitation or file was created in tests.
